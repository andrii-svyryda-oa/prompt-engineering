Claude Code course Lecture 1 · LLMs, agents, capabilities

Overview

Lecture 1

From language models to coding agents

What an LLM is, what an agent is, and what Claude Code can actually do in a repository.

Today

Six things you should leave with

  1. An honest model of an LLM — no mysticism. It predicts the next token from the text already in its window. Fluency is a side effect of predicting text well, not a hidden “understanding module.” It is not a database of your company and not a source of truth.
  2. Why a chatbot is not an agent. A chatbot only returns text; you copy it, run tests, and paste errors. An agent is the same model with tools: it can read files, run commands, see the results, and continue without you as the hands.
  3. The loop that finishes work: gather → act → verify → repeat. Agents stop when the work looks done. Design the job so a check (pytest, ruff, a build, a screenshot) can return pass or fail without you watching every line.
  4. A concrete menu of what Claude Code can do in a repo. Explore without editing, implement from a spec, fix a bug from a symptom, refactor to an existing pattern, run the test/lint loop, and later touch git and Jira through tools — a menu, not a promise.
  5. What still belongs to you, specifically. Architecture tradeoffs, user harm, secrets, production writes, merge to main, and whether the spec was right. “Never delete the database” in English is a request; a hook or a missing tool is enforcement.
  6. How to talk to it on day one so the loop can close. Name the file and the HTTP contract. Point with @path. Define done as tests + linters. Separate explore from edit. Ask for command output. Interrupt and redirect instead of restarting.

Definition

An LLM predicts the next token

A large language model turns the text it has already seen into the next piece of text — a token — then the next, then the next. A token is one unit: sometimes a word, sometimes part of a word, sometimes def or =>. Usefulness is a side effect of predicting text well, including a lot of source code.

def add(a, b):
    return a + b
def add ( a , b ): return a + b

Approximate split, for teaching — not a tokenizer dump. One short function is already a dozen tokens. A 400-line file or a long pytest traceback is thousands.

What that implies

A generator — not a source of truth

Keep this list. You will need it when a demo looks magical.

It isIt is notSo do not expect
A generator trained on a lot of text and code A database of your company It to “already know” your services, ticket IDs, or last week’s decision
Limited by a token window A compiler or test runner Text that looks like a command to be the same as a command that ran
Often fluent and often useful Deterministic The same prompt to produce the same answer twice
Allowed to use only the tools the harness offers Your access-control system Prose like “never delete prod” to block a tool that is still available

People call this hallucination. Here it means fluent tokens where a fact or a check should be — invented APIs, invented ticket IDs, or “the tests passed.” An agent can write that invention into the repo. Tools reduce some of it (it can grep); they do not remove it.

Tokens

The window is big — and shared

Limits and cost are a count of tokens, not a count of files. Modern models have big windows: many Claude Code sessions are on the order of 200k tokens; some models go to 1M. That budget is what one model call can see: your prompt so far, files it read, tool output, and the reply it is writing — they share the count.

Kind~200k tokens can hold~1M tokens can hold
English prose ~150,000 words — a short book ~750,000 words
Source code on the order of 10,000+ lines, or tens of typical files a mid-size repo in one gulp
Test traces / logs a few verbose pytest dumps can take a large slice still easy to fill with noise

You do not need to count them. Big is not infinite: it only sees what still fits in this call.

Pricing

You pay for tokens, not files

API pricing is token count × a rate, published per million tokens. Two meters on every model call: input (what this call sends to the model) and output (what the model writes back). Output is typically about five times the input rate. Bigger, stronger models cost more per token. Exact dollars change; this shape does not.

MeterWhat it countsHow cost moves
Input Prompt so far, files it read, tool results, prior turns Linear in how full the window is this call
Output The reply — including the text of tool calls Linear in how long it talks; the expensive meter
Cached input A repeated prefix (system prompt, tools) A fraction of fresh input, if that prefix did not change

Each agent step is a new model call. A verbose pytest dump is not a one-off: it is input now, and again on the next turn, until it falls out of the window. That is why noisy logs are expensive even when the window is big.

Claude Code in class is usually a subscription, not a raw API key. The same meters still run underneath. Hitting a usage cap is hitting this budget.

“Knowing”

Training vs this session — do not mix them

People say “Claude knows X” for two jobs that look the same in chat. A session is one conversation with its own window. Persistent knowledge has to live in files.

Training

“Knows Python”

Given Python-looking text, it continues with more Python that often compiles. That knowledge is in the weights. It survives every new session.

This session

“Knows our repo”

Only after it has read files, tickets, errors, and CLAUDE.md. There is no permanent copy of your repo inside the model. Next session starts empty of that chat.

Dies with the session

  • The back-and-forth you just had
  • Files it read but never wrote down
  • Style you explained only in chat

Survives a new session

  • CLAUDE.md, rules, skills, docs
  • Tickets and MCP results you fetch again
  • Git history, tests, the repo itself

“Claude forgot our coding style” usually means “new session, nothing was written down.” Lecture 2 is how you reload the useful parts on purpose.

The trap

A chatbot puts you in the middle

A chatbot can help you write a function. It falls apart when the job is “make this repository correct.” An agent is the same model with tools: it calls them, reads the results, and continues until the task is done — or you stop it.

Chatbot — you are the hands

You type → it replies with text You copy, run tests, paste the error Repeat until you are tired

Agent — tools are the hands

You assign a task and a check It reads, edits, runs pytest… You review evidence, not every keystroke

That loop is gather → act → verify. Design the job so it can close without you. If there is no check, you are the check.

pytest, ruff, a build, a screenshot — pass or fail. Failed? Loop. Passed? Show the output. Stuck? Ask you.

Product

Claude Code = model + tools + harness

Without tools it can only talk. With tools, text becomes requests the app executes — and only tools the harness offered. The harness is why two people with the same model get different results. Class default: the terminal CLI in the project folder.

Harness

The product around them

Permissions, CLAUDE.md, skills, hooks, compaction, checkpoints, the UI. You configure this in Lecture 2.

Tools

The hands

Files, search, shell (tests, git, linters), web, subagents, later MCP (Jira). Claude sees a name, a description, and a schema — not a magical understanding of Jira.

Model

The predictor

Reasons, writes, chooses which tool to call next. Still just predicting tokens, now conditioned on tool results.

Day one

Explore first, then define done

A menu, not a promise: explore, implement from a spec, fix a bug, refactor to a pattern, run tests — later git and MCP. Weak prompts (“fix tickets”) invent a plausible nicer. Strong ones name the file, the contract, pytest + ruff, and the output.

Explore — no edits

You are in CampusDesk. Do not change any files.
1. What does this app do?
2. How do I run it and test it?
3. Where would I add a new field on a ticket?

Then a check

Add PATCH from @docs/specs/SPEC-001.md.
Write tests from the acceptance criteria.
Run pytest and ruff. Fix until green.
Show the command output.

If it starts rewriting the README, stop it. Put “no edits” in the prompt. Habit: read first, change second, measure always.

Limits

It will still fail at these — and you will still try

Honesty saves hours. The agent accelerates the middle. The ends stay human.

  • Vague taste — “make the API nicer” produces a random nicer. Write the nicer down.
  • Secrets and production — no production credentials in chat; no unsupervised writes to production Jira.
  • Private facts — if it is not in the repo, the ticket, MCP, or the web, it will fill the gap with a plausible sentence.
  • Huge messy sessions — after enough files and stack traces, quality drops. That is context, not laziness.
  • Policy written only in English — “Never edit .env” in CLAUDE.md is a request. A hook that blocks the edit is enforcement.

Safety

Permissions — cycle with Shift+Tab

Claude Code asks before many actions, depending on permission mode. On some Windows terminals the shortcut is Alt+M. Start with Manual or Accept edits. Use Plan when the task is a whole feature. Do not start with Bypass because a slide looked cool.

ModeFeelWhen
ManualAsks before edits and shellFirst sessions, unfamiliar repos
Accept editsEdits freely, still asks for risky shellOnce you trust the task and the folder
PlanReads and proposes, no source editsAnything that will become a PR
AutoA classifier allows most, blocks scaryLater, when you know the allowlist
BypassAlmost no promptsIsolated environments only

Safety

Checkpoints are not git — interrupt, don’t restart

Before file edits, Claude Code snapshots the files. Double Esc can rewind conversation and files. Remote side effects do not rewind. When it goes the wrong way, say what was wrong; restart when the job changed or the context is junk.

Checkpoints can undo

Local file edits in this session. Useful when the approach is wrong and you want the files back.

Checkpoints cannot undo

Jira transitions, git push, dropped tables, anything that left the laptop. Git is the real undo for commits. Permissions and hooks are the real undo for tools that leave the machine.

  • Esc — stop this turn. Type a correction while it works.
  • Reject a tool call if the command should not run.
  • Plan mode when the task is a PR-sized change.
