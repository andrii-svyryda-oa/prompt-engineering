Lecture 5

Spec-driven development

Agents build a coherent system. A spec makes them build the system you needed.

Today

Six things you should leave with

  1. The spec is the contract. Code is the implementation. If it is not in the spec, Claude must not build it. If it is in the spec, tests must prove it. This is the opposite of vibe coding, where the prompt evaporates when the session ends.
  2. Write a spec an agent can implement without guessing. Numbered requirements, an honest Out of scope, acceptance criteria that become tests, checks (pytest, ruff), and open questions that mean stop — not invent.
  3. The loop: explore → spec → plan → implement → verify → docs → ticket. Plan mode until the spec is signed. Then implement only that spec. Map each acceptance line to a test. Update architecture in the same change.
  4. Keep the lanes: git holds the contract, Jira holds the queue. Two copies will drift. The ticket should point at docs/specs/SPEC-xxx.md. MCP opens the file; it does not improvise from a one-liner.
  5. Refuse scope expansion unless the spec changes first. “Add assignee” attracts a user table, email, and an admin UI because those tokens often follow. Out of scope is the most important section for agents.
  6. MCP is transport, not a second spec. Read the issue, write or link the file in git, implement from the file, comment a summary. You own status transitions — helpful agents love clicking Done.

The boring failure

Fluent extras nobody asked for

Agents are trained to complete patterns. A ticket that says “add assignee” will attract a full user table, email notifications, and an admin UI, because those tokens often follow “assignee” on the internet.

A human intern who overbuilds can be glared at. An agent overbuilds fluently and quickly, then writes docs that justify the extra work. Without a spec, review is you arguing with a very fast junior.

Definition

Pin the pattern to a document you control

If it is not in the spec, Claude must not build it. If it is in the spec, tests must prove it.

This lecture is not enterprise theater. It is the smallest set of documents and habits that let an agent loop close against a written contract. You already have the machinery: the loop (L1), project memory (L2), modes and MCP (L3), context (L4). SDD is how you point that machinery at one source of truth.

Contract

Five rules, not a ceremony

  1. Work starts with a written spec — markdown in the repo, or a Jira story that is the spec.
  2. The spec lists behavior, acceptance, out of scope, and checks.
  3. Implementation may not add product behavior that is not in the spec.
  4. Tests are traced to acceptance criteria.
  5. If reality disagrees, you change the spec first (or explicitly waive), then the code.

Canonical

Git holds the contract. Jira holds the ticket.

Jira is excellent as a queue: priorities, assignees, status. Jira is a poor unique home for a 3-page spec. Two copies will drift.

Canonical spec: docs/specs/SPEC-001-ticket-assignee.md

MCP should open the file, not improvise from a one-liner in the description. If the ticket is a stub, write the SPEC in git first, then comment the path.

Out of scope

The most important section for agents

List the extras that usually follow the pattern on the internet. If you do not write them down, the model will treat them as implied.

For “add assignee”

No user directory. No validation that the person exists. No email. No UI. No permissions model.

Why it works

Review becomes mechanical: every extra endpoint is a spec miss, not a taste argument. The agent can be told “nothing from Out of scope” and have a file to obey.

Good vs bad

Implementable versus “like other tools”

Bad

“Add assignees like other tools.” The model will invent a User, a foreign key, and a notification.

Good

R1 optional string | null. R4 omit on PATCH leaves the value unchanged. Clearing uses null. No user directory.

## Acceptance
- Given a new ticket without assignee, GET shows null.
- PATCH {"assignee":"it-oncall"} then GET shows that value.
- PATCH {"assignee":null} then GET shows null.

Tests

The spec in executable form

With a spec, review is mechanical: every criterion has a test or a reason it is manual; no extra endpoints; docs match the spec, not the agent’s blog post.

  • Name tests after the spec id (test_spec001_assignee_defaults_null).
  • Do not rewrite tests to match accidental behavior.
  • Optional TDD: failing tests first, then code until green. Agents are good at this when you forbid extra fixtures.

MCP

Transport, not a second spec

  1. Read the issue. If it is a stub, write the SPEC in git and comment the path.
  2. Implement from the file, not from a one-line summary the model invented.
  3. Comment a short summary of what shipped and what you refused.
  4. You own status. Do not let “helpfulness” move the ticket to Done.

Docs

Update architecture in the same change

When docs and code disagree, the next agent will pick at random. Keep docs short so they can be found without eating the window.

  • New field on Ticket → one paragraph in architecture.md, not a new chapter.
  • Do not paste the whole spec into CLAUDE.md.
  • Product copy that did not change does not need a rewrite “for completeness.”
