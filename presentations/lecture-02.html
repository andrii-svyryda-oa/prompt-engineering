Lecture 2

How Claude reads a project

CLAUDE.md, linked docs, rules, skills, hooks — and a setup order that does not drown the model.

Today

Six things you should leave with

  1. A session is not empty when you type “hi.” System prompt, root CLAUDE.md, unscoped rules, skill descriptions, and MCP names are already in the window. Reads, path-scoped rules, skill bodies, and hook output accumulate later.
  2. Prose teaches. Settings configure. Hooks enforce. CLAUDE.md is markdown advice the model may ignore. settings.json is machinery. If you need “cannot rm -rf,” that is a hook or a deny — not italics.
  3. Write a short, checkable CLAUDE.md and commit it. Put facts the code will not say: run/test/lint commands, package manager, where new code goes, project-specific always/never. Target under ~200 lines. Vague “be clean” does not belong.
  4. @ in CLAUDE.md is a tax every session. Imports expand at launch. @ in one prompt is paid once. Do not import the wiki. Import a short architecture note — or only mention the path.
  5. Choose a layer: always / sometimes / must. Always true and short → CLAUDE.md. Always true only in app/ → path-scoped rule. Multi-step and occasional → skill. Must happen even if Claude forgets → hook.
  6. A setup order that stops when the next layer has no trigger. Honest README and tests first. /init then cut. /context to prove it loaded. Allowlist pytest and ruff. Add rules, one skill, one hook only when you have a repeatable mistake to prevent.

Test for every line

Would deleting this cause a repeatable mistake?

If no, do not add it. The trap is collecting every feature: memory files, rules, skills, hooks, plugins, subagents, MCP. You do not need all of them on day one. You need the right layer for each kind of knowledge.

Long instructions are not stronger. They are easier to ignore.

Before you type

The session is not empty

A new session is not a blank model plus your first sentence. Setup is already in the window. Work then piles on.

Already in

Paid before “hi”

System prompt · root CLAUDE.md and unscoped rules · auto memory (capped) · skill descriptions, not bodies · MCP names (schemas often later).

Then grows

Paid as it works

Each Read · path-scoped rules and nested CLAUDE.md when matching files are opened · skill bodies on / or a match · hook output after edits.

Habit

/context is how you know it loaded

It shows the pie of what actually occupied the window — not what you hoped was loaded. Run it after /init and whenever the agent starts ignoring a rule you are sure you wrote.

  • If CLAUDE.md is missing from Memory files, you are in the wrong directory or the file is named wrong.
  • If Memory files is 800 lines, you imported too much. Cut, or move chapters into path-scoped rules.
  • Launch inside the project folder, not the course root.

CLAUDE.md

Standing instructions, every session

You write it. It is the replacement for repeating yourself. Files concatenate — they do not override like CSS. Contradictions make Claude pick at random.

ScopeWhereWho
User~/.claude/CLAUDE.mdYou, all projects
Project./CLAUDE.mdThe team — commit it
Local./CLAUDE.local.mdYou, this repo — gitignore
Nestedpackage/CLAUDE.mdLoads when working in that subtree

Claude also walks up the tree. Launching in apps/api/ can load three files. In a monorepo that is powerful and noisy.

Write this

Facts the code will not say clearly

Put what Claude cannot infer reliably. Leave out tutorials, catalogs of every endpoint, and “be professional.”

Put in

  • How to run, test, lint, typecheck
  • Package manager (pnpm vs npm)
  • Always / never that is project-specific
  • Where new code goes (routes vs store)
  • Gotchas: in-memory store, shared test state

Leave out

  • A restatement of the README
  • The whole architecture wiki
  • “Write clean code”
  • Anything a path-scoped rule or skill should own

Target under ~200 lines. If removing a line would not cause a mistake, remove it.

Specificity

Checkable beats polite

The model is good at sounding like it followed you. Give it a command it can run and output it must show.

Vague

“Test your changes.” “Format properly.” “Don’t break anything.” Claude will write a confident paragraph and stop.

Checkable

“Before done: pytest and ruff check .. Show the last lines of output. Do not say done without them.”

/init

Generate, then cut

/init drafts a CLAUDE.md from the repo. Useful as a first pass. Often too long — it catalogs files instead of stating the few facts that prevent mistakes.

  • Keep the commands, the layout, the gotchas.
  • Delete the rest. Then run /context and /doctor.
  • /doctor flags the obvious: missing files, bad names, secrets in the wrong place.

Linked docs

@path in CLAUDE.md is paid every session

Imports expand at launch. Nested hops are limited. Backticks keep @README as literal text instead of an import.

See @README.md for how to run.
Architecture: @docs/architecture.md

Every session

@ inside CLAUDE.md — the file is in the window even for “rename this variable.”

This once

@docs/specs/SPEC-001.md in a prompt — tax this task, then it can leave.

Do not import the wiki. Import a short architecture note — or only mention the path so Claude can open it when the task needs it.

Rules

.claude/rules/ splits topics

Unscoped rules load at start — same tax as CLAUDE.md. Path-scoped rules load when matching files are read, which is how you keep Python style out of a markdown-only session.

---
paths:
  - "app/**/*.py"
  - "tests/**/*.py"
---
# Keep handlers thin. Tests ship with endpoints.

One topic per file. If two rules contradict, Claude picks at random — same as stacked CLAUDE.md files.

Skills

Procedures that wait until needed

A folder plus SKILL.md becomes /folder-name. Claude sees the description up front (cheap). The body loads on / or when the task matches (paid then).

Good skill

“Finish a change”: run pytest and ruff, show output, update the spec status, do not invent scope.

Bad skill

A 2,000-line playbook that restates the wiki. Put important lines at the top — compaction may keep only the head.

Older .claude/commands/*.md still works. New work uses skills.

Choose a layer

Four homes for knowledge

If you put a multi-step ritual in CLAUDE.md, you pay for it on every rename. If you put a hard safety rule only in prose, it will be ignored on a busy day.

NeedPut it inWhy
Always true, shortCLAUDE.mdEvery session, cheap if small
Always true, only in app/Path-scoped ruleLoads when those files are read
Multi-step, sometimesSkillDescription now, body on demand
Must happen even if Claude forgetsHook or denyThe product enforces it

Hooks

Advice is optional. Hooks are not.

A hook is a command the product runs at an event. Output can enter the conversation — keep it short. A 5,000-line log on every edit is how you poison the window.

EventTypical use
PreToolUseBlock rm -rf, block writes to .env
PostToolUseRun ruff after Edit/Write — a short summary, not the full file
StopRefuse “done” if pytest is red

/hooks is what is actually registered. The JSON on disk is intent. If they disagree, trust the live panel.

Gitignore

Team memory is committed. Secrets are not.

CLAUDE.local.md
.claude/settings.local.json
  • Never commit tokens, API keys, or .mcp.json that embeds secrets.
  • Team CLAUDE.md, .claude/settings.json, rules, and skills should be committed so the next engineer gets the same loop.
  • Your allowlist for pytest can stay local if the team has not agreed yet.

Debug

When “it doesn’t follow the rules”

Usually the file is not loaded, it is buried, or the rule was only advice. Check the live product before rewriting the paragraph.

  • /context — loaded? 800 lines of Memory files?
  • /skills — wrong folder name, so / does not match?
  • /hooks — JSON on disk but nothing registered?
  • Dangerous action still happens → hook or deny, not another sentence in italics
