# Практичне заняття 10 — End-to-end: story → специфікація → цикл → докази

**Мова:** українська · [English](../10-end-to-end-story.md)

**Час:** 90–120 хвилин  
**Коли:** Останнє основне практичне заняття  
**Залежить від:** Практик 5–9

## Мета

Пройдіть **весь цикл курсу** на одній новій фічі для CampusDesk, так, ніби ви працюєте в реальній команді з Jira та репозиторієм.

Оберіть **одну** фічу зі списку. Не робіть дві.

| ID | Фіча | Примітки |
| --- | --- | --- |
| A | Ticket tags | `tags: list[str]`, макс. 8, lowercase, PATCH замінює все |
| B | Resolved_at | Встановлювати, коли status стає `resolved`, очищати, якщо знову відкрито |
| C | Сортування списку | `?sort=created_at|priority` із задокументованим типовим значенням |
| D | Issue, призначене викладачем | Справжній ключ Jira з практики 9 |

Якщо обираєте D, issue в Jira має мати справжню специфікацію (або ви спочатку пишете SPEC-00x і коментуєте шлях).

## Поза межами для всіх варіантів

Автентифікація, база даних, UI-фреймворк, email, Slack, видалення тікетів, пагінація (хіба що сама специфікація вимагає лише пагінацію, але у варіантах вище цього немає).

## Порядок дій (виконуйте по черзі)

### 1. Черга (Queue)

- **Справжня Jira:** створіть або використайте Story; description вказує на шлях до специфікації.
- **Mock:** додайте `docs/jira-mock/CAMP-2xx.md` так само.

### 2. Специфікація в git

`docs/specs/SPEC-00x-….md` — статус `approved`, розділ Open questions порожній, критерії приймання придатні для написання тестів.

Усе має бути готове до коміту. Виконуєте роль апрувера ви.

### 3. Нова сесія, режим Plan

```text
/implement-spec @docs/specs/SPEC-00x-....md
Також прочитай тікет у Jira/mock. Якщо вони суперечать одне одному, зупинись і скажи мені.
```

Усі розбіжності вирішуйте **через зміну специфікації або тікета**, а не намагаючись знайти компроміс у коді.

### 4. Реалізація + цикл перевірки

Приймайте зміни (Accept edits). Використовуйте `pytest -q`, `ruff`, а також хуки/скіли, які у вас уже є. Локально запускаєте тести ви самі.

### 5. Документація

Викличте `/sync-docs` або еквівалент. Оновіть `http-examples`, якщо змінився API.

### 6. Закрийте цикл на тікеті

- **Справжня:** залиште коментар зі шляхом до специфікації, назвами тестів та залишком ризиків. **Не** переводьте в статус Done, хіба що викладач сказав, що ваше Definition of Done дозволяє це зробити.
- **Mock:** додайте розділ `## Implementation` з тією самою інформацією.

### 7. Аналіз контексту

Скріншот `/context` або маркований список: що «з'їло» найбільше контексту. Одне речення про те, що б ви зробили інакше (використали б субагента, прибрали б зайвий вивід у тестах, зменшили б кількість MCP-дампів тощо).

## Результат (для портфоліо)

Один markdown-звіт `docs/practice-10-report.md` у застосунку:

- Обрана фіча
- Ключ тікета / шлях до mock-файлу
- Шлях до специфікації
- Назви тестів, прив'язані до критеріїв приймання
- Вивід `pytest` / `ruff`
- Текст коментаря в Jira або розділ реалізації в mock
- Список файлів у diff
- Рефлексія щодо контексту (5–10 рядків)

## Що вважається провалом (Fail bar)

Завдання не зараховується, якщо є хоча б один із таких пунктів:

- Немає файлу специфікації
- Додано фічі або поведінку, яких немає в специфікації
- Тести не відповідають критеріям приймання
- Тільки модель написала, що тести зелені (без вашого запуску)
- У фіналі тікет і специфікація суперечать одне одному
- Закомічено секрети

## Додатково

Відкрийте pull request (або файл патча), у описі якого — ID специфікації + список тестів. Попросіть Claude написати опис для PR **на основі специфікації**, а потім видаліть із тексту весь зайвий маркетинг чи "хайп".
