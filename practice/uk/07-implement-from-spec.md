# Практичне заняття 7 — Реалізація за специфікацією

**Мова:** українська · [English](../07-implement-from-spec.md)

**Час:** 70–100 хвилин  
**Коли:** після практичного заняття 6 і лекції 5  
**Залежить від:** `docs/specs/SPEC-001-ticket-assignee.md` у статусі `approved`

## Мета

У **новій або очищеній сесії** реалізуйте виключно SPEC-001. Тести мають відповідати критеріям приймання. Працюйте, доки pytest і ruff не стануть зеленими. Оновіть документацію, якщо поведінка системи змінилася.

## Завдання

### 1. Skill (якщо його ще немає)

Створіть `.claude/skills/implement-spec/SKILL.md`, як описано в лекції 5 §6 (можете адаптувати формулювання). В CLAUDE.md має бути вказівка для Claude використовувати його.

### 2. Свіжий контекст

```bash
cd practice/starter-campusdesk
claude --permission-mode plan
```

**Не** продовжуйте сесію з практичного заняття 6, якщо там уже накопичилося багато діалогів. Використати `/clear` — цілком нормально.

### 3. План за файлом

```text
/implement-spec @docs/specs/SPEC-001-ticket-assignee.md
```

або еквівалентний промпт з лекції. **Зупиніться на етапі створення плану.** Перевірте, чи:

- відсутня таблиця User
- тести названі або описані відповідно до кожного критерію приймання
- зміни стосуються лише store, models, routes та tests

### 4. Опційний підхід TDD (рекомендовано)

```text
Спочатку напиши тести в pytest для кожного критерію приймання, які свідомо падають.
Запусти pytest -q; вони мають падати з правильної причини.
Після цього пиши реалізацію, поки тести не позеленіють. Не спрощуй тести, щоб підлаштуватися під випадково написаний код.
```

Якщо часу обмаль, реалізуйте тести в один хід із кодом — але все одно **опираючись на специфікацію**, а не на код, який ви вже написали.

### 5. Цикл перевірки

```text
Запускай pytest -q та ruff check ., доки перевірки не стануть зеленими. Покажи вивід.
```

Після цього **ви** самостійно запускаєте ці ж команди локально.

### 6. Документація

Оновіть `docs/architecture.md` (нове поле та семантика PATCH) і `docs/product.md`, якщо змінилася логіка, з якою взаємодіє користувач. Змініть статус специфікації на `implemented`.

### 7. Перегляд diff (людиною)

Відкрийте diff. Видаліть усе, чого немає в SPEC-001. Якщо ви дуже хотіли додати якусь фічу, спершу опишіть її в SPEC-002.

## Результат

- Реалізація + тести
- Статус специфікації змінено на `implemented`
- Скопійований план від Claude
- Вивід pytest та ruff з вашого термінала
- Список файлів з diff, де кожен файл прив'язаний до розділу специфікації або має позначку «docs»

## Що вважається провалом (Fail bar)

- Зайві endpoints
- Поле `assignee` зроблено обов'язковим
- Тихе встановлення дефолтного значення `"unassigned"` замість `null` без змін у специфікації
- Тести, які не перевіряють, що повертає GET
- CLAUDE.md тепер містить повний текст специфікації

## Додатково

Додайте негативний тест: PATCH з `"assignee": ""` — **але тільки якщо** ви спершу оновите SPEC-001, вказавши там очікувану поведінку (відхиляти запит чи сприймати як `null`). Специфікація завжди первинна.
