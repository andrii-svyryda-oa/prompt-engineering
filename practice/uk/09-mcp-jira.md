# Практичне заняття 9 — Інструменти MCP і історії Jira

**Мова:** українська · [English](../09-mcp-jira.md)

**Час:** 60–90 хвилин  
**Коли:** Після лекцій 3 і 5  
**Залежить від:** Налаштування Claude для CampusDesk з попередніх практик

## Мета

Підключіть **Atlassian MCP** (або mock-шлях), **прочитайте** історію, **створіть** історію і напишіть skill, щоб Claude не вигадував власний workflow (статуси, assignees, production-проєкти).

Якщо у вашій аудиторії немає Jira Cloud: повністю виконайте **частину B (mock)**. Частина A обов'язкова, коли викладачі видали доступ.

---

## Частина A — Живий Atlassian MCP (коли доступний)

Офіційні URL змінюються. Надавайте перевагу актуальній документації Atlassian + Claude Code. Типове встановлення в Claude Code:

```bash
claude mcp add --transport http atlassian https://mcp.atlassian.com/v2/mcp
```

Потім у сесії:

```text
/mcp
```

Авторизуйтеся. Підтвердіть, що інструменти з'явилися.

Використовуйте **ключ навчального проєкту** (приклад `CAMP`), ніколи не production-дошку.

### A1. Читання

```text
Перелічіть нещодавні issues у проєкті CAMP (або ключ, який нам дали).
Оберіть один. Стисло опишіть title, status, критерії приймання.
Не змінюйте жоден issue.
Якщо критеріїв немає, скажіть це явно.
```

**Залік:** Справжній ключ issue і чесне «критеріїв немає», якщо їх немає.

### A2. Створення з файлу специфікації

```text
Створіть Story у навчальному проєкті.
Title: SPEC-001 Ticket assignee (course)
Description: канонічний шлях специфікації docs/specs/SPEC-001-ticket-assignee.md
плюс короткий виклад на 5 рядків. Не вставляйте всю специфікацію.
Не призначайте виконавця. Не змінюйте статус. Поверніть ключ.
```

**Залік:** Ключ повернуто. Ви відкриваєте Jira в браузері і підтверджуєте, що issue існує.

### A3. Обережність щодо дозволів

```text
Чи вважається коментар до цього issue дією запису (write)? Запитай мене перед будь-яким записом.
```

Потім, **лише якщо викладач дозволяє коментарі**:

```text
Додайте коментар: "Курс, практика 9 — агент підключено. Зміни статусу немає."
```

### A4. Skill

`.claude/skills/jira-story/SKILL.md`:

- Типово: лише читання, якщо користувач не каже створити/прокоментувати
- Завжди включайте шлях специфікації в description, коли специфікація існує
- Ніколи не змінюйте статус (transition)
- Ніколи не видаляйте
- Надавайте перевагу git-специфікації як канонічній

### A5. `/context`

Занотуйте частку MCP на діаграмі після `get_issue`, який повернув багато полів. Якщо вона величезна, додайте в skill: «стисло підсумовуйте; не повторюйте custom fields».

## Частина B — Mock MCP (завжди доступний)

Навіть якщо частина A вдалася, зробіть B, щоб можна було працювати офлайн.

1. Створіть `docs/jira-mock/CAMP-101.md` наче це issue з JSON, розгорнутий у markdown:

```markdown
# CAMP-101
Type: Story
Status: To Do
Title: Ticket tags
Description: Див. Open questions — не готово.

## Acceptance
(немає)
```

2. Створіть `docs/jira-mock/CAMP-102.md` з **повною** мініспецифікацією для чогось уже реалізованого (наприклад, запит за status з практики 5), щоб «прочитати тікет» мало зміст.

3. Промпт:

```text
Вважайте docs/jira-mock/*.md за Jira. Живого MCP немає.
Прочитайте CAMP-102. Переформулюйте критерії приймання. Не редагуйте mock.
```

4. Промпт:

```text
Створіть новий mock issue CAMP-103 з @docs/specs/SPEC-001-ticket-assignee.md
як короткий тікет, що вказує на шлях специфікації. Запишіть лише файл.
```

**Залік:** CAMP-103 існує і не дублює всю специфікацію.

---

## Результат

- Частина A: ключ issue + скріншот `/mcp` **або** письмовий блокер (немає доступу)
- Частина B: mock-файли, включно з CAMP-103
- Skill `jira-story`
- Один абзац: як Claude **бачить** інструменти MCP (name, description, schema, result) застосовано до того, що ви спостерігали

## Безпека

Жодних продакшен-токенів у git. Не комітьте `.mcp.json` із заголовками Authorization. Лише MCP у user-scope або змінні оточення.
