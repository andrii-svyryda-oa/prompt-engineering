# Практичне заняття 5 — Цикл розробки на реальній зміні

**Мова:** українська · [English](../05-development-loop.md)

**Час:** 70–90 хвилин  
**Коли:** після лекції 3  
**Залежить від:** практичних занять 1–4

## Мета

Реалізувати **невелику зміну за специфікацією**: спершу в режимі Plan, потім в Accept edits, і врешті — прогнати цикл перевірок, доки все не буде «зеленим». Поки без Jira і жодних зайвих функцій.

## Зміна (це ваша специфікація)

Додайте необов’язковий параметр запиту (query parameter) для списку тікетів:

`GET /tickets?status=open|in_progress|resolved`

Правила:

- Якщо `status` не передано → поведінка залишається такою, як зараз (повертаються всі тікети).
- Якщо `status` невалідний → повертаємо **422** (помилка валідації), а не 500.
- Фільтрація здійснюється за точним збігом значення з полем `status` тікета.
- Тестові дані (seed data) та наявні тести мають і надалі проходити без помилок.
- Нові тести повинні покривати: фільтрацію за статусом `open`, фільтрацію з порожнім результатом та передачу невалідного значення.

Що виходить за межі завдання (Out of scope): пагінація (pagination), пошук (search), авторизація (auth), збереження в базу (persistence), UI.

## Завдання

### 1. Чиста сесія в CampusDesk

```bash
cd practice/starter-campusdesk
claude --permission-mode plan
```

### 2. Створення плану

```text
@docs/architecture.md @app/main.py @app/store.py @tests/test_tickets.py
Спроектуй GET /tickets?status=... так, як описано в моєму завданні (Practice 5).
Напиши план: які файли потрібно змінити, як назвати тести та якою буде поведінка при невалідному status.
Не пиши реалізацію коду. Не додавай пагінацію чи пошук.
```

**Пройдено, якщо:** план згадує `list_tickets` / параметр запиту / pytest. Якщо агент пропонує додати SQL-базу чи користувачів — відхиліть ці пропозиції в чаті.

### 3. Реалізуйте з доказами

Вийдіть із режиму Plan. Вставте наступний промпт:

```text
Реалізуй виключно затверджений план.
Зроби тести для трьох випадків: працюючий фільтр, порожній результат та невалідний статус.
Запускай pytest -q та ruff check . доки все не буде зеленим.
Покажи вивід команд.
```

Наприкінці використайте `/verify-change`, якщо ви створювали такий skill.

### 4. Запустіть перевірки самостійно

У звичайному терміналі (не лише через Claude) виконайте:

```bash
pytest -q
ruff check .
```

**Пройдено, якщо:** перевірки успішно проходять на **вашій** машині.

### 5. Ручна перевірка HTTP

Запустіть сервер (`uvicorn app.main:app --reload` або подібне). Зробіть запити на:

- `/tickets`
- `/tickets?status=open`
- `/tickets?status=nope` (тут очікуйте помилку 422)

### 6. Аналіз контексту

Виконайте `/context` — зверніть увагу, чи не стала сесія занадто перевантаженою (heavy). Якщо ви відволіклися на інші теми в процесі розмови, поясніть, чому варто було б виконати `/clear`.

## Результат

- Написаний код та тести.
- Текст затвердженого плану (вставка).
- Вивід виконання `pytest` і `ruff`.
- *Необов’язково:* знімок екрана зі сторінки OpenAPI (`/docs`), де видно новий параметр.

## Критерії оцінювання

| Незалік | Причина |
| --- | --- |
| Немає нових тестів | Цикл розробки не завершено. |
| Невалідний `status` повертає 500 | Порушено контракт API. |
| Реалізовано зайві функції | Не дотримано обмежень завдання (Out of scope). |
| Лише Claude написав «зелено» | Ви не запускали `pytest` самостійно локально. |

## Завдання із зірочкою

Реалізуйте можливість передавати кілька статусів через кому `?status=open,in_progress`. **Не робіть цього, якщо не напишете ще два додаткові тести.** Якщо ви не можете або не хочете писати ці тести — вважайте це завдання поза межами (out of scope).
