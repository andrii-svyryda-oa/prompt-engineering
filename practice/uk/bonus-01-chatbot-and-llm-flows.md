# Бонус 1 — Чатбот або LLM-флоу всередині CampusDesk

**Мова:** українська · [English](../bonus-01-chatbot-and-llm-flows.md)

**Час:** 3–5 годин (можна розбити на два підходи)  
**Коли:** після практики 10  
**Рівень:** бонус. Основний курс вважається завершеним і без цього.

## Мета

Додайте в продукт **невелику фічу на базі мовної моделі**. Спочатку напишіть для неї специфікацію, а потім реалізуйте, використовуючи той самий цикл роботи з агентом, до якого ви вже звикли.

Оберіть **один** варіант.

| Трек | Що ви будуєте | Навіщо це існує |
| --- | --- | --- |
| **A. Чатбот підтримки** | `POST /chat` — користувач ставить запитання про тікети / як працює CampusDesk; сервер викликає LLM і повертає відповідь | Помічник для користувача |
| **B. LLM-флоу** | **Пайплайн** із 2-3 промптів зі структурованим виводом, UI чату не потрібен — напр. «стисло підсумувати цей тікет + коментарі → пропозиція пріоритету + чернетка відповіді в один рядок» | Бекенд-процес |

Обидва варіанти мають бути **безпечними для агента**: жодних прихованих записів та необмеженого доступу до інструментів (це буде в Бонусі 2).

## Обов'язкові розділи специфікації

Напишіть `docs/specs/SPEC-B1-llm-feature.md` до початку роботи з кодом.

Включіть:

1. **Користувач / той, хто робить виклик** — хто звертається до endpoint.
2. **Вхідний / вихідний JSON** — точні формати даних.
3. **Провайдер моделі** — сумісний з OpenAI HTTP, Anthropic або **mock-провайдер** для тестів (див. нижче).
4. **Що моделі дозволено відповідати** — напр. вона може підсумовувати тікети, які їй дали; але вона не може вигадувати id тікетів.
5. **Таймаути та збої** — 4xx проти 5xx, і що робити, якщо провайдер впав.
6. **Секрети** — API-ключ має бути у змінних середовища, ніколи не логуватися і ніколи не потрапляти в git.
7. **Поза межами** — жодного RAG по всьому інтернету, жодних записів у Jira, жодного агентного циклу з інструментами (це Бонус 2).
8. **Тести** — щонайменше перевірки на:
   - помилку провайдера → повертається визначений код статусу
   - невалідне тіло запиту → 422
   - успішний сценарій з **mock-LLM** (не робіть реальних мережевих запитів у pytest)

## Фіктивний провайдер (обов'язково для CI)

**Не** змушуйте unit-тести звертатися до платного API.

Шаблон:

```text
app/llm.py          # клієнт; читає CAMPUSDESK_LLM_BASE_URL + ключ
tests/conftest.py   # monkeypatch або httpx mock
```

pytest використовує mock-відповідь. Окремий скрипт для ручного запуску або розділ у README може викликати реальну модель, якщо у студента є ключ.

## Начерк варіанту A (це не специфікація)

`POST /chat`

```json
{ "message": "Як очистити assignee?", "ticket_id": null }
```

Сервер:

1. Якщо передано `ticket_id`, завантажте цей тікет (поверніть 404, якщо його не знайдено).
2. Сформуйте промпт: system («ти — помічник CampusDesk, використовуй лише переданий JSON тікета та стислі факти про продукт») + повідомлення користувача.
3. Викличте LLM.
4. Поверніть `{ "reply": "...", "used_ticket_id": 1 | null }`.

Факти для system-промпту варто брати з **короткого** рядка тексту або уривка з `docs/product.md`, скопійованого в код. Не треба давати моделі необмежений доступ до читання всіх файлів репозиторію.

## Начерк варіанту B (це не специфікація)

`POST /tickets/{id}/suggest`

Пайплайн:

1. Промпт 1: JSON `{ "summary": str, "priority": "low"|"medium"|"high" }`
2. Промпт 2: JSON `{ "reply_draft": str }` на основі summary
3. Поверніть обидва результати. Якщо JSON із першого промпту не розпарсився → повертайте 502 з кодом помилки, без нескінченних спроб повтору (retry storm).

## Додатково

Додайте прапорець `dry_run: true`, який повертатиме згенерований **промпт** без фактичного виклику провайдера. Це неймовірно корисно для дебагу та навчання. Спочатку додайте це в специфікацію.
