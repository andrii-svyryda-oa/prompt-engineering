# Практичне заняття 3 — Rules, skills і пов’язані документи

**Мова:** українська · [English](../03-rules-skills-linked-docs.md)

**Час:** 60–80 хвилин  
**Коли:** після лекції 2  
**Залежить від:** практичного заняття 2 (файл `CLAUDE.md` має існувати)

## Мета

Розділити знання так, як ми обговорювали на лекції 2: створити path-scoped **rule**, **skill**, яку можна викликати через `/`, і свідомо вирішити, що саме імпортувати, а що — лише згадувати.

## Завдання

### 1. Path-scoped rule

Створіть `.claude/rules/python-api.md`:

```markdown
---
paths:
  - "app/**/*.py"
  - "tests/**/*.py"
---

# CampusDesk Python

- Обробники маршрутів (route handlers) мають залишатися тонкими; бізнес-логіку тримайте у `store.py` (або в окремому модулі сервісу).
- Нові ендпоінти та поля тікета слід додавати разом із відповідними тестами (pytest) в одному коміті.
- Не додавайте бази даних, авторизацію чи зайві залежності, якщо цього не вимагає специфікація.
```

### 2. Глобальне правило (коротке)

Створіть файл `.claude/rules/docs.md` без блоку `paths`:

```markdown
# Docs

- Термінологія продукту: використовуйте "ticket", а не "issue" (хіба що йдеться про Jira).
- Специфікації живуть у `docs/specs/` (коли вони з’являться).
```

Rules без обмеження за шляхом завантажуються в кожній сесії. Тримайте їх максимально короткими.

### 3. Командна skill

Створіть `.claude/skills/verify-change/SKILL.md`:

```markdown
---
description: Перевірити зміну в CampusDesk. Використовуй, коли користувач каже «випусти», «завершуй», «перевір» або «готово».
---

1. Запусти `pytest -q` та `ruff check .`.
2. Якщо хоча б щось падає, виправ і запускай знову, доки перевірки не стануть успішними або ти не заблокуєшся.
3. Якщо змінилася видима для користувача поведінка, вкажи, чи потрібно оновити документацію в `docs/`. Пиши коротко (не пиши роман).
4. Перелічи змінені файли, виконані команди та можливі ризики, що залишилися.
5. Не роби коміт, якщо тебе про це не просили.
```

### 4. Почистьте `CLAUDE.md`

Якщо ваш `CLAUDE.md` тепер дублює правила про Python, **видаліть ці дублікати**. Натомість вкажіть на нове правило одним рядком: «Правила Python API: `.claude/rules/python-api.md`.»

Вирішіть для себе:

- Залишити імпорт `@docs/product.md` **або** замінити його на «читай `docs/product.md`, коли завдання стосується продукту».
- Запишіть одне речення у свої нотатки, пояснивши компроміс щодо використання токенів (про це йшлося в лекціях 2 і 4).

### 5. Тестування автоматичного виклику та слеш-команди

Відкрийте нову сесію.

```text
Я закінчив невелику зміну. Завершуй роботу.
```

Перевірте, чи обере Claude автоматично skill `/verify-change` (він може це зробити, а може й ні). Після цього явно викличте її:

```text
/verify-change
```

**Пройдено, якщо:** агент запускає pytest та ruff (вам потрібно буде підтвердити використання інструментів) і показує вивід.

### 6. Перевірте path-scoped rule

```text
@app/main.py
Якщо я додаю нове поле, де має жити валідація? Відповідай одним абзацом.
```

**Пройдено, якщо:** агент аргументує на користь models/store, а не «товстого» маршруту, як і вимагає наше правило.

### 7. `/skills` і `/context`

Переконайтеся, що skill відображається у списку. Зверніть увагу, чи з’являються файли rules і за яких умов.

## Результат

- Два файли rules і одна skill.
- Почищений файл `CLAUDE.md`.
- Два збережені транскрипти або скриншоти: виконання `/verify-change` та відповідь на запитання «де має жити валідація».

## Завдання із зірочкою

Додайте `disable-model-invocation: true` у frontmatter skill. Переконайтеся, що просте прохання «завершуй» більше не підвантажує skill автоматично, але виклик `/verify-change` і далі працює. Після цього вирішіть, яка саме поведінка краще підійде для вашої команди, і залиште відповідний коментар у файлі skill.
