## Як читати цей конспект

Це лекція про налаштування (setup). Після неї ви маєте вміти зайти в репозиторій і залишити після себе такий setup для Claude, за який інший інженер скаже вам дякую.

Головна пастка — тягнути в проєкт усі фічі одразу. У Claude Code їх багато: файли пам’яті, rules, skills, hooks, plugins, субагенти, MCP. Вони не потрібні вам у перший же день. Вам потрібен правильний **шар** для кожного виду знання.

Корисна перевірка для кожного рядка, який ви додаєте:

> Якщо ми це видалимо, чи почне Claude робити **повторювану** помилку?

Якщо ні — не додавайте. Довгі інструкції не сильніші. Їх просто легше ігнорувати.

## Навчальні цілі

1. Описати, що вже є у вікні до того, як ви почали друкувати, а що накопичується під час роботи агента. І використати `/context`, щоб довести, що воно справді завантажилось.
2. Розрізняти три шари: проза (`CLAUDE.md`) навчає, `settings.json` конфігурує, а hooks і deny — змушують.
3. Писати короткий, перевірюваний `CLAUDE.md` з фактами, яких немає в коді. До 200 рядків, комітити в репозиторій, жодних порад типу «пишіть чисто».
4. Використовувати імпорти `@`, не перетворюючи вікі на оперативну пам'ять: за `@` у `CLAUDE.md` ви платите кожну сесію, а за `@` у промпті — лише раз.
5. Свідомо обирати шар: завжди істинне і коротке → `CLAUDE.md`; стосується лише `app/` → path-scoped rule; багатокрокове і рідкісне → skill; має виконатись, навіть якщо Claude забуде → hook.
6. Налаштовувати проєкт покроково і зупинятись, якщо для наступного шару ще немає реальної потреби. А також дебажити проблеми «він ігнорує правила» через `/context`, `/skills` і `/hooks`, а не переписуванням абзаців тексту.

## 1. Мапа `.claude`

Коли ви запускаєте `claude` у проєкті, Claude Code дивиться у робочу директорію та у вашу домашню папку. Адекватно налаштований проєкт виглядає десь так:

```
your-project/
  CLAUDE.md                 # інструкції команди (commit)
  CLAUDE.local.md           # ваші нотатки (gitignore)
  .mcp.json                 # командні MCP-сервери без секретів (commit)
  .claude/
    settings.json           # дозволи, hooks, політика проєкту (commit)
    settings.local.json     # ваші allowlists (gitignore)
    rules/
      testing.md
      api.md
    skills/
      ship-ticket/
        SKILL.md
    commands/               # старіше місце для slash-команд; усе ще працює
    agents/                 # власні означення субагентів, пізніше
```

Файли на рівні користувача живуть у `~/.claude/` (`CLAUDE.md`, `skills/`, `rules/`, `settings.json`). Тримайте там власні вподобання, а не архітектурні рішення команди.

> **Одним реченням:** прозові файли навчають; `settings.json` конфігурує; hooks примушують; skills чекають, доки знадобляться.

### Settings проти CLAUDE.md

Їх часто плутають.

| | `CLAUDE.md` | `.claude/settings.json` |
| --- | --- | --- |
| Мова | Markdown, поради | JSON, механіка |
| Приклади | «Запусти `pytest`, перш ніж казати, що готово» | allowlists дозволів, hooks, env |
| Примусово? | Ні. Модель може проігнорувати | Так, це жорсткі обмеження на рівні продукту |
| Токени | Так, з'їдає вікно контексту | Здебільшого ні, окрім виводу hook |

Якщо ви хочете заборонити Claude робити `rm -rf`, вам потрібен **hook** або **permission deny**, а не грізний абзац тексту.

## 2. Що завантажується ще до вашого першого слова

Нова сесія — це **не** чистий аркуш, де є лише ваше перше повідомлення. Ще до того, як ви торкнетеся клавіатури, Claude Code зазвичай закидає в контекст:

- системний промпт (інструкції до інструментів, поведінка продукту)
- **`CLAUDE.md` у корені проєкту** і глобальні rules
- **auto memory** (нотатки, які Claude залишив сам собі, вони лімітовані)
- **імена й описи skills** (не повні тіла skills)
- **імена інструментів MCP** (повні схеми часто відкладають, доки інструмент не використають)
- можливо, output style або додатковий системний промпт, який ви налаштували

Далі, в процесі роботи:

- кожен **Read** додає текст файлу
- **path-scoped rules** і **вкладені `CLAUDE.md`** підвантажуються, коли агент читає відповідні файли
- **вміст skills** підвантажується, коли ви самі пишете `/skill-name` або коли Claude розуміє, що час його застосувати
- **hooks** можуть дописати вивід (наприклад, результат лінтера після правки)

Саме тому `/context` — професійна звичка. Він показує кругову діаграму того, що насправді зайняло вікно, а не те, що ви сподівалися туди покласти.

Запускайте його після `/init`. Якщо `CLAUDE.md` немає серед Memory files, ви або не в тій директорії, або файл названо з помилкою.

## 3. CLAUDE.md — базові інструкції

`CLAUDE.md` — markdown-файл, який Claude читає на старті **кожної** сесії в цьому scope. Ви його пишете. Це спосіб не повторювати одне й те саме щоразу.

### Де живуть файли (від широкого до конкретного)

| Scope | Розташування | Для кого |
| --- | --- | --- |
| Managed / org | системний шлях політики | На всю компанію, керується IT |
| User | `~/.claude/CLAUDE.md` | Ви, усі проєкти |
| Project | `./CLAUDE.md` або `./.claude/CLAUDE.md` | Для команди, іде в коміт |
| Local | `./CLAUDE.local.md` | Для вас, лише в цьому репозиторії, ігнорується git |
| Nested | `package/CLAUDE.md` | Підвантажується, коли Claude працює в тому піддереві |

Ці файли **склеюються**. Вони не перекривають один одного, як стилі в CSS. Більш специфічні інструкції йдуть останніми. Це зручно, але якщо є **суперечності**, Claude просто вгадуватиме. Не допускайте цього.

Claude також іде **вгору** деревом тек. Запуск у `apps/api/` може підвантажити `apps/api/CLAUDE.md`, і `apps/CLAUDE.md`, і кореневий `CLAUDE.md` репозиторію. У монорепозиторіях це крута, але дуже шумна фіча. Є налаштування `claudeMdExcludes` для «будь ласка, ігноруй файл іншої команди.»

### Що класти всередину

Пишіть те, про що Claude не зможе здогадатися з коду:

- як проєкт запускати, тестувати, лінтити й тайпчекати
- менеджер пакетів (`pnpm` vs `npm`)
- «завжди / ніколи», специфічні для проєкту
- де живуть фічі («маршрути в `app/main.py`, правила в `store.py`»)
- правила git та PR (але лише якщо ви їх справді дотримуєтесь)
- змінні середовища, потрібні для запуску
- підводні камені («in-memory store скидається; тести ділять стан процесу»)

### Чого там бути не повинно

- туторіали та історичні довідки
- повні довідники API (давайте посилання або робіть skill)
- стандартні мовні поради, які Claude вже має («пиши чистий код»)
- усе, що змінюється щотижня (дати кладіть у specs, не в CLAUDE.md)
- екскурсію репозиторієм файл за файлом

Офіційна порада Anthropic: тримайте файл **до 200 рядків**. Якщо видалення рядка не призведе до помилок у роботі агента — сміливо його видаляйте.

### Як написати рядок так, щоб його виконували

Вода: «Форматуй код правильно.»  
Конкретика: «Python: ruff, довжина рядка 100, як у `pyproject.toml`.»

Вода: «Тестуй свої зміни.»  
Конкретика: «Перш ніж сказати, що задача готова, запусти `pytest` і `ruff check .` і встав підсумок.»

Вода: «Будь обережним із базою даних.»  
Конкретика: «Не запускай деструктивний SQL. У цьому навчальному застосунку немає production-бази.»

Якщо якесь правило агент усе одно ігнорує, можете виділити **саме цей рядок**. Але якщо ви виділите двадцять рядків, магія зникне.

### `/init`

`/init` оглядає репозиторій і створює чернетку `CLAUDE.md`. Якщо файл уже є, пропонує покращення, а не сліпо перезаписує.

Використовуйте це як **заготовку**, а потім нещадно ріжте. Згенеровані файли зазвичай задовгі й пишуть очевидні речі. Пізніше запустіть `/doctor`: він підкаже, які інструкції можна видалити, бо Claude і так бачить їх у коді.

### Auto memory

Окрім `CLAUDE.md`, Claude вміє зберігати **auto memory** (свої спостереження та ваші виправлення). Цей файл завантажується на старті сесії та має ліміт (десь 200 рядків або 25KB).

- Ви пишете `CLAUDE.md` для команди.
- Claude пише auto memory для патернів, які помітив.

Не ставтеся до auto memory як до архітектурного документа. Якщо якесь правило має працювати для всієї команди, ручками перенесіть його в `CLAUDE.md` або в rule.

`/memory` відкриває файли. Заглядайте туди, коли ловите себе на думці «він же мав це запам'ятати».

## 4. Пов’язані документи (імпорти `@`)

Усередині `CLAUDE.md` можна лінкувати інші файли:

```markdown
Див. @README.md, як запускати застосунок.
Архітектура: @docs/architecture.md
Намір продукту: @docs/product.md
```

Що треба знати:

- Імпорти **розгортаються під час запуску** прямо у вікно контексту. Вони не безкоштовні.
- Відносні шляхи рахуються від **файлу, де написаний імпорт**, а не від вашої поточної директорії.
- Імпорти можуть вкладатися, з невеликим лімітом стрибків (порядку чотирьох).
- У бектиках `@README` — це просто текст. Без них — це імпорт.
- Коли проєкт вперше намагається імпортувати щось **за межами** робочої директорії (наприклад, з `~/.claude/...`), Claude Code попросить дозволу. Це не баг, це безпека.

### Коли імпортувати

Імпортуйте **короткі** архітектурні нотатки або шматок README на 40 рядків, без яких модель просто не зможе працювати.

**Не** імпортуйте:

- увесь експорт Confluence
- згенерований OpenAPI JSON
- огляд дизайну за минулий квартал

Такі речі краще ховати у **skill** (завантажиться, коли треба) або просто згадувати через `@` **у конкретному промпті**.

> **Одним реченням:** `@` у `CLAUDE.md` означає «плати цю вартість токенів кожну сесію»; `@` у промпті означає «заплати один раз.»

### AGENTS.md та інші інструменти

Claude Code за замовчуванням читає `CLAUDE.md`, а не `AGENTS.md`. Якщо в репозиторії вже є `AGENTS.md` для інших агентів, найкраще зробити так:

```markdown
@AGENTS.md

## Claude Code
Для всього, що чіпає `app/store.py`, використовуй режим Plan.
```

`/init` також може затягнути rule-файли в стилі Cursor / Copilot у чернетку `CLAUDE.md`.

## 5. Rules — `.claude/rules/`

Коли `CLAUDE.md` розростається на розділи, час його розбити.

Кладіть markdown-файли в `.claude/rules/`:

```
.claude/rules/
  testing.md
  python-style.md
  http-api.md
```

Глобальні rules завантажуються на старті сесії, так само як і `CLAUDE.md`.

### Path-scoped rules

```markdown
---
paths:
  - "app/**/*.py"
  - "tests/**/*.py"
---

# Python у CampusDesk

- Бізнес-правила живуть у `store.py` або в модулі сервісу, не в маршруті.
- Нові endpoints їдуть разом із тестами в тій самій зміні.
```

Вони завантажуються лише тоді, коли Claude **читає ці файли**. Це економить токени, якщо ви сьогодні взагалі не чіпаєте Python.

Якщо правило має пережити стискання контексту (compaction) і діяти завжди, робіть його глобальним або пишіть у кореневий `CLAUDE.md`. Path-scoped rules можуть стиснутися разом з історією, а потім підвантажитися знову, коли агент знову звернеться до файлу.

Для власних звичок є `~/.claude/rules/` («я люблю явну типізацію»). Не тягніть це в загальний репозиторій.

## 6. Skills — процедури на вимогу

**Skill** — це тека з `SKILL.md`. Назва папки стає командою, наприклад `/folder-name`.

Claude одразу бачить лише **опис**. А от **вміст** завантажується, коли:

- ви самі пишете `/ship-ticket`, або
- Claude розуміє, що ваш запит підходить під опис

У цьому вся суть. Саме завдяки skills ваш `CLAUDE.md` залишається компактним.

Користувацькі slash-команди раніше жили як `.claude/commands/foo.md`. Це все ще працює. Але нові речі краще створювати в `.claude/skills/foo/SKILL.md`. Той самий `/foo`.

### Skill, який варто написати

Якщо ви щоразу копіпастите один і той самий чекліст на 20 рядків, щоб «закрити тікет» — вам потрібен skill.

```markdown
---
description: Завершити зміну коду в CampusDesk. Використовуй, коли користувач просить випустити, обгорнути або перевірити фічу тікета.
---

## Завершити зміну

1. Запусти `pytest` і `ruff check .`.
2. Якщо щось падає, виправ і перезапусти. Не зупиняйся на першому зеленому файлі, якщо набір тестів червоний.
3. Оновлюй `docs/` лише якщо змінилася видима користувачеві поведінка.
4. Стисло: змінені файли, запущені тести, залишковий ризик.

Не коміть, якщо користувач не просив.
```

Необов’язкові поля YAML (залежать від продукту, але варто знати):

- `disable-model-invocation: true` — лише ви можете його запустити через `/name`. Забороняє агенту викликати його самостійно.
- `context: fork` — виконати skill у субагенті, щоб уся його робота з файлами не засмічувала ваш основний контекст.

Skills також вміють підставляти реальний вивід термінала через синтаксис `!` `` command ``. Тому skill «зроби саммарі мого diff» може чесно виконати `git diff`, а не фантазувати.

### Skill проти CLAUDE.md проти rule

| Потреба | Куди класти |
| --- | --- |
| Завжди істинне, коротке | `CLAUDE.md` |
| Завжди істинне, але лише в `app/` | path-scoped rule |
| Багатокрокова процедура, іноді | skill |
| Має виконатися, навіть якщо Claude «забуде» | hook |

### Де живуть skills

| Місце | Шлях |
| --- | --- |
| Проєкт (команда) | `.claude/skills/<name>/SKILL.md` |
| Користувач | `~/.claude/skills/<name>/SKILL.md` |
| Plugin | усередині встановленого plugin |

`/skills` показує, що бачить ця сесія. Якщо вашого skill немає, неправильна назва теки чи frontmatter, або ви запустили Claude не з тієї директорії.

## 7. Hooks — рутина, про яку можна забути

**Hook** — це команда, HTTP-виклик, промпт або субагент, який Claude Code запускає на **події життєвого циклу**.

Пораду в markdown агент може проігнорувати. Hook — ні. Якщо вам потрібно «кожна Python-правка відформатована» або «ніколи не пиши в `.env`», використовуйте hook.

### Події, які ми реально будемо налаштовувати

| Подія | Коли | Типове використання |
| --- | --- | --- |
| `PreToolUse` | Перед запуском інструмента | Блокувати `rm -rf`, блокувати запис секретів |
| `PostToolUse` | Після успішного інструмента | Запустити ruff на редагованому файлі |
| `Stop` | Claude вважає, що готово | Запустити повний набір тестів; не дати зупинитися, якщо тести впали |
| `SessionStart` | Сесія починається | Надрукувати ім’я репозиторію, нагадати про гілку |
| `PreCompact` | Перед стисканням контексту | Зберегти нотатки, які вам важливі |

Є ще багато подій (дозволи, субагенти, compaction). Вам не обов'язково їх знати, щоб здати курс. Головне зрозуміти принцип: **hooks працюють на рівні інфраструктури, а не покладаються на добрі наміри моделі.**

### Як це виглядає в settings

Hooks живуть під `"hooks"` у файлі settings, а не в якомусь лівому `hooks.json` у корені (plugins використовують `hooks/hooks.json`; проєкти зазвичай — `.claude/settings.json`).

Концептуальний приклад PostToolUse:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "ruff check ${CLAUDE_PROJECT_DIR}"
          }
        ]
      }
    ]
  }
}
```

Точні назви матчерів і полів JSON можуть змінюватися від версії до версії. Тому на практиці робимо так: просимо Claude **написати hook**, а потім перевіряємо через `/hooks`, чи він підхопився. `/hooks` — це реальність. Файл на диску — лише ваші наміри.

### Вивід hook — це контекст

Якщо PostToolUse hook друкує помилки лінтера, цей текст іде назад у розмову. Це добре: агент може їх виправити. Це також **коштує токени**. Hook, який на кожну правку випльовує лог на 5 000 рядків, просто вб'є вам сесію. Друкуйте короткий підсумок.

### Stop hooks і «готово»

Stop hook може відмовитися завершити хід, доки `pytest` не пройде. Так можна змусити агента фіксити баги самостійно. Claude Code не дозволить кривому Stop hook заблокувати вас назавжди — там є ліміт на кількість спроб. Але все одно: пишіть скрипти так, щоб вони падали зі зрозумілою помилкою.

> **Одним реченням:** skills кажуть Claude, як випускати код; hooks не дають випустити зламане.

## 8. Дозволи та локальні налаштування

`.claude/settings.json` (комітиться) може дозволяти `pytest`, `ruff`, `git status` і забороняти очевидно дурні команди.

`.claude/settings.local.json` (у gitignore) — місце, куди **ви** кладете додаткові allowlists, щоб не воювати з командним конфігом.

`CLAUDE.local.md` — текстовий аналог «це суто для мене»: URL вашої пісочниці, ваш тестовий користувач.

Завжди додавайте в gitignore:

```
CLAUDE.local.md
.claude/settings.local.json
```

І ніколи не комітьте API-токени. `.mcp.json` можна комітити **без** секретів; для токенів використовуйте змінні середовища або MCP у user-scope. Лекція 3.

## 9. Рекомендований setup проєкту (робіть саме в такому порядку)

Це ідеальний флоу як для пар, так і для реальної роботи. Зупиняйтеся, якщо для наступного кроку ще немає реальної потреби.

### Крок 0 — Зробіть репозиторій чесним

- README, інструкції з якого реально працюють
- одна команда тестів
- одна команда лінта
- коротка архітектурна нотатка

Якщо люди не можуть запустити перевірки, агент теж не може.

### Крок 1 — `/init`, потім безжалісно ріжте

Згенеруйте `CLAUDE.md`. Видаліть усе, що код уже показує. Залиште команди і підводні камені. Закомітьте.

### Крок 2 — `/context` і `/doctor`

Переконайтеся, що файл завантажився. Приберіть суперечності.

### Крок 3 — Дозволи для внутрішнього циклу

Дозвольте команди тестів і лінта, яким довіряєте. Сидіть у режимі Manual або Accept edits, доки не відчуєте впевненість.

### Крок 4 — Path-scoped rules

Коли в `CLAUDE.md` виростає розділ «Python» і розділ «docs», рознесіть їх по окремих файлах.

### Крок 5 — Один skill для рутини команди

Приклад: `/verify-change`, який запускає pytest + ruff і за потреби оновлює docs.

### Крок 6 — Hooks для речей, про які всі постійно забувають

Format-on-edit або тести через Stop-hook. Почніть з одного hook. Дивіться `/hooks`.

### Крок 7 — MCP, коли починається суцільний копіпаст

Jira, Slack, Figma, база даних. Не раніше. Кожен MCP-сервер додає імена інструментів (а іноді набагато більше) у світ, який бачить модель.

### Крок 8 — Лише тоді: додаткові агенти, plugins, наворочені workflow

Якщо почати з кроку 8, у вас буде музей YAML-конфігів і модель, яка все ще не вміє запускати тести.

### Командні звички

- Робіть рев'ю `CLAUDE.md` у PR так само, як і коду.
- Якщо Claude двічі робить ту саму помилку, правте конфіг, а не псуйте собі нерви.
- Якщо правило критичне, це має бути hook або перевірка в CI, а не текст курсивом.
- Документи, які ви імпортуєте через `@`, тримайте короткими, інакше ви платитимете за них токенами кожну сесію.

## 10. Як Claude «бачить» усе це разом

Уявіть, що ви просите: «Додай поле assignee до тікетів.»

1. Кореневий `CLAUDE.md` уже пояснив: моделі в `models.py`, store у `store.py`, тести обов’язкові.
2. Claude читає `app/models.py`. Підвантажується path-scoped API rule.
3. Опис `/ship-ticket` збігається з «завершити фічу»; Claude може підвантажити цей skill наприкінці.
4. Після кожної правки PostToolUse hook запускає ruff. Вивід з’являється в транскрипті.
5. Ви ніколи не згадували ruff. Це зробила інфраструктура проєкту.

Це **налаштований** агент. Та сама модель, що в колеги з порожнім репозиторієм, але результат кардинально інший.

Якщо щось «не працює»:

| Симптом | Перевірте |
| --- | --- |
| Ігнорує стиль | `/context` — чи завантажився файл? Може, там 800 рядків тексту? |
| Немає skill | `/skills`, назву папки, поточну директорію |
| Немає hook | `/hooks`, JSON у settings, matcher |
| Усе одно робить небезпечне | hook / deny rule, а не ще один абзац тексту |

`/debug`, `/doctor` і `claude --safe-mode` існують саме для ситуацій «у моїх конфігах завелися привиди». Safe mode вимикає всі кастомізації, щоб ви зрозуміли: тупить модель чи ваш музей налаштувань.

## 11. `CLAUDE.md` для CampusDesk, який варто закомітити

Ось такого формату цілком вистачить для Практичних 2–4:

```markdown
# CampusDesk

## Команди
- Встановлення: `pip install -e ".[dev]"`
- Запуск: `uvicorn app.main:app --reload`
- Тести: `pytest`
- Лінт: `ruff check .`

## Архітектура
- FastAPI-застосунок у `app/main.py`
- Pydantic-моделі в `app/models.py`
- In-memory store у `app/store.py` (скидається після перезапуску)
- Намір продукту: @docs/product.md
- Архітектура: @docs/architecture.md

## Правила
- Тримайте обробники маршрутів тонкими.
- Кожна зміна поведінки потребує pytest.
- Не додавайте auth, persistence чи нові залежності, якщо цього немає в spec.
- Перш ніж казати, що готово: `pytest` і `ruff check .` зелені. Покажіть вивід.
```

Зверніть увагу: жодних романів, жодних копіпастів з документації FastAPI і жодних «будь корисним асистентом».

## Підсумок

- Старт сесії підвантажує базову пам'ять, **описи** skills і **імена** MCP — а не всі документи вашого проєкту.
- `CLAUDE.md` працює завжди, він короткий, конкретний і лежить у git.
- Імпорти `@` у `CLAUDE.md` теж працюють завжди, тому використовуйте їх економно.
- Rules допомагають розбити інструкції за темами; `paths` дозволяють завантажувати їх лише тоді, коли треба.
- Skills — це ваші кастомні `/commands` і покрокові інструкції на вимогу.
- Hooks і settings — це жорсткі правила; markdown — лише побажання.
- Налаштовуйте в порядку: чесний репозиторій → маленький CLAUDE.md → дозволи → rules → один skill → один hook → MCP.

## Питання для самоперевірки

1. Чому `CLAUDE.md` на 600 рядків може зробити Claude *менш* слухняним?
2. Вам потрібен чекліст релізу на 15 кроків, яким користуються двічі на місяць. CLAUDE.md, rule, skill чи hook?
3. Ви хочете, щоб ruff запускався після кожної правки файлу, навіть якщо Claude забуде. Який шар?
4. У чому різниця між `@docs/architecture.md` у `CLAUDE.md` і прикріпленням `@docs/architecture.md` в одному промпті?
5. Skill вашого колеги не підтягується. Назвіть три місця, куди ви б подивилися.
6. Навіщо класти `CLAUDE.local.md` у gitignore?
